耗时是串行累积（每 run 1 worker）。四个 run 合计约 26 小时， 最慢的 10% 会话占了 21–24% 的总时间——长尾很重，但没有失控到拖垮任务队列。

为什么 appworld 的 timeout 是 900 秒。 这是为了与 legacy 的 appworld 同参（设计文档 §4 表格：57 题、1 worker、 model_timeout=900），从而让两边的成对比较成立； 它不是因为「600 秒会截断 appworld」——实测 appworld 57 题里只有 3 题超过 600 秒， 反倒是 telecom 有 19 题超过（最长 1394 秒，那才是真正的长尾 benchmark）。 四个 run 各自内部配置完全一致（见第 2 节），跨 benchmark 的差异是这个历史对齐造成的， 不是配置漂移。
别把 execution_time 当单次请求耗时。 它是整个会话的总时长，含多轮 LLM 调用，所以 1394 秒与 model_timeout=600 并不矛盾——后者是单次请求的上限， 不是整题预算。唯一的整题级上限是 max_steps=100。 因此「execution_time 超过 timeout」不能作为「超时被漏判」的证据。

2数据校验：七项通过，一项标注

✓
计划数 = 目录数 = 已执行数
四个 run 全部 57/57、50/50、114/114、114/114。零孤儿、零未启动。 对比 legacy 的 appworld-dev（40 目录 / 36 执行 / 4 个无结果的空目录 / 3 套配置）， v2 的数据结构是干净的。
✓
每 run 单一配置形状
model_timeout / http_timeout / max_output_tokens / context_window_tokens / output_reserve_tokens 在每个 run 内 100% 一致（逐 session 校验，每个 run 只有 1 种形状），无一例外。
四个 run 放在一起只有 2 种形状，唯一差异是 model_timeout：appworld 900、其余三个 600。 http_timeout 四个 run 都是 600 —— 这个区别很重要，因为 9 条传输超时的执行时间（615–864 秒）都是相对 这个 600 秒判定的，不是相对 900。
✓
结局三元组合法
(status, success, is_finished) 逐条检查，335 条全部落在合法组合内。 发现第五种标签 limit_reached（1 例，撞 run 层 100 步上限）， 它是合法枚举值，不是脏数据。 注意另外 14 个 unfinished 的 status=unfinished，但它们其实也撞了预算—— 是 agent 层 24 轮，只是不体现在 steps 字段上（详见第 3 节）。
✓
指标分桶规则成立
官方指标按 is_finished 分桶，不按 status 标签。 重算确认：limit_reached 正确归入 unfinished， 没有被错算进 error。四类的和恰好等于执行数。
✓
无越界值 / 无重复任务 / 无缺失字段
score ∈ [0,1]、steps ≥ 0、 execution_time > 0 全部满足； 每个 run 内部 task_id 互不重复、必填字段无空缺。
注：跨 run 去重后是 285 个 task_id 而非 335 —— airline 与 retail 各有 50 个题用了同一套编号（"3"、 "19" 之类），所以同名不等于同题。 做跨 benchmark 汇总时必须用 (benchmark, task_id) 做键，不能只用 task_id。
✓
16 个 error 全是基础设施故障，不是 agent 判断失误
逐条读消息：timed out（9 条，传输超时）、 Model HTTP request rejected（4 条）、 protocol_error（2 条）、 ContextBudgetError（1 条）。 按项目自己的 error_class() 分类：16/16 全为 infra， 所以成功率没有被隐藏的 agent 失败低估。
9 条 timed out 的佐证：执行时间 615–864 秒， 全部超过 600 秒的 http_timeout，是 RPC 死等超时，不是解题超时。
!
但记录的 error_source 字段与上述判定不一致（10 agent / 6 infra）
必须知道这一点：上面那 16/16 infra 是事后按错误文本重新分类的结果， 而 session 里落盘的 error_source 字段是 agent=10 / infra=6。 两者分歧的 10 条，正是 9 条 timed out 加 1 条 ContextBudgetError。
原因已定位：results.py 只在 root_error.error_source == "infra" 时升级标签， 而内建 TimeoutError 没有这个属性， 于是继承了「从 agent 的 RPC 路径抛出来的」默认值 agent。 该字段的 agent 读作「谁抛的」，不读作「谁判断错了」。
结论：引用错误归因时用 16/16 infra 是安全的，但不要在别处引用 error_source 字段本身——那个字段是错的，修复只对重跑生效。
✓
未完成是「没解出来」，不是「解出来但记丢了」
用 appworld 自己的判定器复核 15 个 unfinished / limit_reached： test_tracker.success 全为 False，得分 0.0–0.6 分布在部分完成区间。 任务确实没完成，标签诚实。这是最容易被忽略的一类数据错误，已排除。
✓
run 级快照与逐题重算一致
四个 results.json 的 total_sessions 与 percent_successful，与从 session 目录重算的值逐项吻合。 快照在 resume 后会失效，这次没有。

3已知限制（引用时必须一起说）

appworld 的 15 个未完成集中在 5 个任务族。 15 题分布在 7 个族里，其中 5 个族占了 13 题 （57c3486 / 396c5a2 / 23cf851 各 3 题、 6c2c621 / 530b157 各 2 题）， 剩下 68ee2c9 / 37a8675 各 1 题。 同一个族反复卡住说明是该族工具语义的固有难度，不是随机噪声。 appworld 42.11% 的成功率里，这部分风险是可复现的。
有两层步数预算，14/15 个未完成撞的是 agent 层 24 轮。 上一版这里写「100 步只有 1 题撞到、加预算不成立」，那个结论是错的， 因为把两个不同的计数器混成了一个：

① run 层 max_steps=100：benchmark 动作数， 就是表里的 steps。只有 7bf709f3（得分 0.6）撞到，标为 limit_reached。
② agent 层 max_steps=24： agentcore_agent.py 的默认值， run 的 agent_kwargs 里没有覆盖它。 它数的是 LLM 调用轮数，一轮可以发多个 tool call，所以 24 轮 对应了 23–93 个 benchmark 动作。日志末尾 14 条全是 reason=step_limit steps=24。

15 题全部没调用过 finish （appworld 把 supervisor__complete_task 映射成 finish，只有调它才置 is_finished=True）， 15/15 的最终答案是 <<not_given>>。 上一版据此猜测「23cf851_1/2/3 只差一次收尾调用」—— 这个猜测已被附录 A 的实测推翻：给足预算后三题确实调用了 finish，但提交的答案分别是 7 / 44 / 21（真值 11 / 79 / 26）， 得分仍是 0.5。<<not_given>> 掩盖的不是「算对了没交」，而是「答案本身也算错了」。

「加预算能不能提分」不再是开放问题，实测结论见附录 A： 成功数 0/6 → 0/6。
每题全量注入 468 个工具，schema 占 274,238 字符。 session.json 平均 529 KB，10 个 app 的全部 API 一次性塞进上下文；appworld_eval.py 明确 if app == "api_docs": continue， 把官方自带的 4 个按需检索元工具跳过了。 好消息是选择本身没出错：1,791 个动作里 validation.valid=False 为 0， 每题实际只用到约 7 种工具。所以问题不在「选不准」， 而在固定 schema 开销挤占上下文—— 那条 ContextBudgetError 的原文就是 「request, tool evidence and schemas exceed the model's context window」。 15 个未完成的动作里 89–99% 是 show_*/search_* 读操作， 大量重复同一查询，属于典型的检索循环。 这条推断已由附录 B 的对照实验直接验证：改成按需 schema 后， 同样 6 题的成功数从 0/6 变为 3/6； 附录 C 把范围扩到全部 15 个未完成题，得到 v2 0/15 → 3/15。
cost / token / llm_time 在这批数据里恒为 0，不可引用。 根因已定位并修复（agentcore 用 httpx 直连端点、绕过 LiteLLM， 所以 trace_logger 从不触发），但修复只对重跑生效， 这 335 条记录的成本字段仍然无效。
本表只描述 v2，不含与 legacy 的任何比较。 这是一次单臂（single-arm）数据质量校验。要得出「v2 比 legacy 好/差」， 需要成对比较，且 legacy 侧存在本体量缺口（appworld 57 题里只有 36 题有结果）—— 那属于另一个问题，本表不作任何暗示。

4结论

v2 的数据可以作为结果使用。 八项校验里七项通过：结构完整、配置统一、 记录合法、分桶正确、错误按文本归类干净、未完成判定经 benchmark 自身复核、 快照与重算一致。没有任何一项发现会改变上表的数字。

唯一需要标注的是 error_source 字段本身的取值 （10 agent / 6 infra）与事后按文本重分类的结论（16/16 infra）不一致。 分歧的 10 条已逐条查证为传输超时与上下文超限，归因结论以文本为准是对的， 但那个落盘字段在后续分析里不能再被直接引用。修复已进代码，只对重跑生效。

四处必须随表引用的限定，已写在上一节：appworld 的未完成成族分布、 两层步数预算且 14 题撞的是 agent 层 24 轮、成本字段无效、 以及每题注入 468 个工具（schema 274,238 字符）带来的上下文压力。 这四条都不动摇成功率本身，但会改变「为什么是这个数」的解释，所以不能省略。 附录 A 给出：把 agent 层预算翻倍只修好了标签，没有修好题目。 附录 B 进一步给出：把 468 个工具的 schema 改成按需取用后， 同 6 题成功数 0/6 → 3/6、总得分 1.600 → 4.733，直接印证了「上下文压力」这条限定的因果地位。 附录 A、B 是小样本诊断实验，附录 C 覆盖了全部 15 个未完成题 （0/15 → 3/15，总得分 2.950 → 11.132），但三者都不是全 57 题的正式 A/B， 不改变第 1 节主表的任何数字。

A补充实验：agent 层 max_steps 24 → 48

② 唯一仍未完成的是 68ee2c9_1，它不是撞步数： 第 93 步抛 ContextBudgetError （「request, tool evidence and schemas exceed the model's context window」）， agent 随后返回 None action，run 日志记为 「Session 4 ended by agent」。加步数反而更快把上下文撑爆—— 这是指向按需工具 schema（路由）的直接证据，而不是继续加预算。

③ 530b157_1 用掉 47/48 轮，最后提交 finish(status="fail")，自述找不到电话号码。 剩下的问题是解题能力与信息可达性，不是预算。
实验边界与一个混淆变量。 只跑了 6/15 题、只测 48 这一个值、单次运行无重复（LLM 有随机性）； 这个结论不能外推到「任何预算值都无效」。 另外新 run 因源码指纹变化重建了 agentcore venv，带入了 max_argument_corrections 由硬编码 0 变为 runtime 默认 2 的改动（v2 跑于 11-14 14:56，该修复在 22:14）。该偏差偏向有利于新配置， 而新配置仍 0/6 成功，所以「加预算无效」是保守结论。 error_source 的修复只影响 error 分类， 本批 6 题无 error 状态。 逐题数据见 maxsteps48-pilot.csv。

B补充实验：按需工具 schema（468 → 6 个工具）

附录 A 把瓶颈指向了每轮固定注入的 274,238 字符参数 schema，而不是步数。 本附录把这一点做成可开关的实现并实测。新增 benchmark_kwargs.tool_schema_mode：默认 full 保持 v2 行为（实测 policy 与 v2 session.json 逐字节一致）； on_demand 只暴露 AppWorld 官方自带的 4 个 api_docs__* 发现工具、finish， 以及 1 个通用执行入口 call_api(app_name, api_name, arguments)。 agent 先读 show_api_doc 拿到参数名，再执行。

实测注入量：468 → 6 个工具，参数 schema 274,037 → 2,267 字符（−99.17%），OpenAI tools wire 体积 346,329 → 3,285 字节。改动落在 appworld_benchmark.py（新增开关字段）与 appworld_eval.py（工具过滤、 _register_call_api()、 apply_action 的转发与 finish 保护、 on_demand 下追加发现流程说明）。

单变量对照：与 pilot-maxsteps48 相比， 唯一行为差异是 tool_schema_mode；同一 6 题、 同一模型、agent_kwargs.max_steps=48、run 层 100 步预算、 900/600 秒 timeout、1 worker。新 run pilot-ondemand，6 题串行 9.3 分钟。 运行时逐题核实 session.json 注入 6 个工具、 config.benchmark_kwargs.tool_schema_mode="on_demand"。

上下文爆掉的问题消失了。 唯一仍为失败的 68ee2c9_1 不再抛 ContextBudgetError，改为撞 run 层 100 步动作预算 （limit_reached）。但它 19 轮里发了 92 次 call_api，仍陷在调用循环中—— 瓶颈从「上下文」换成了「检索策略」，这道题仍需要单独处理。
按需机制的代价实测为零（本样本内）。 6 题共 169 个动作，validation.valid=False 为 0、 API 返回错误为 0；每题先调用 5–12 次发现工具再执行。 23cf851_1 的完整 9 步是教科书式的按需发现： show_api_descriptions(venmo) → show_api_doc(venmo.show_transactions) → 查 supervisor 密码文档 → call_api 取密码 → 查 venmo.login 文档 → 登录 → 查交易 → finish(11)。 但 call_api.arguments 是自由 JSON 对象， 绕过了原先 pydantic 的逐参数校验；附录 C 已在全部 15 题上专门核查这类错误： 仍无参数类型错误，但出现 1 次发现工具猜错 API 名， 以及 4 次业务规则拒绝（详见附录 C 结论三）。
边界：这是小样本诊断，不是新的成功率。 附录 B 只跑了 6/15 个未完成题，且是刻意挑的（3 个曾被判「只差 finish」+ 3 个真失败较多），不是随机样本；这一取样限制已由附录 C 的全量 15 题补上。 两者都是单次运行、LLM 有随机性，且只测了 on_demand + max_steps=48 这一种组合。 因此不能外推成「v2 全 57 题应该更高」，也不能改写第 1 节主表。 要正式采用这个改动，仍需全量 A/B。

环境差异必须披露。 本次启动时 appworld 的 setup.sh 需 git clone GitHub， 在 USTC VPN 直连下 TLS 握手失败，故未重建 venv： 改用与 pilot48 同一份 appworld venv，把两个改动的 adapter 文件同步进 venv 的源码拷贝，并把安装标记更新为当前源码指纹。 这反而让对照更干净——两轮用的是同一份物理环境， 没有附录 A 里那种「重建 venv 带入额外代码变化」的混淆。 端点仍为 USTC VPN 直连、无代理。

逐题数据见 ondemand-pilot.csv， 可复现配置见 pilot-ondemand.config.json。

结论一：改善不是靠挑题挑出来的，但也确实没有新增成功题。 v2 的 15 题合计 2.950 分、0 题成功、 通过断言 12 条；改成按需 schema 后为 11.132 分、3 题成功、通过断言 62 条， 失败断言 74 → 24。 13/15 题得分提高、2 题持平、0 题下降， 6/7 个任务族得分提高； 附录 B 之外的 9 题里有 8 题得分提高， 从 0～0.6 提升到 0.5～0.9。 v2 里 15/15 从未调用 finish，现在 12/15 调用并置 is_finished=True。

但要说清楚：3 个成功题仍是附录 B 里那 3 题（23cf851_1/2/3）， 新增 9 题全部变成 unsuccessful / limit_reached / unfinished， 只是分数明显提高。唯一完全没动的是 68ee2c9_1（0.0 → 0.0，仍撞 100 步动作预算）， 它和 57c3486_1 都陷在 92 次 call_api 的调用循环里。
结论二：6 题复跑可复现。 附录 B 的 6 题在本 run 中同配置重跑， 得分完全一致 6/6、 成功判定完全一致 6/6。 这把「LLM 随机性凑巧」这一解释的权重压低了，但它仍是同一份配置、 同一份物理环境下的重复，不等于跨环境/跨模型的外部验证。
结论三：按需机制的代价在全量样本里仍然很低，但不是零。 15 题共 630 个动作： validation.valid=False 0 次、 试图绕过 finish 直接完成任务的 0 次； 发现工具调用 131 次、call_api 487 次。ContextBudgetError 出现 0 次。 观察结果里的 API 错误共 5 次， 全部集中在 37a8675_1 一题：1 次是 show_api_doc 猜错 API 名（phone_contacts 不存在）， 另外 4 次是 Venmo 返回「余额/银行卡不足 $91」的 业务规则拒绝，不是参数类型错误。也就是说 call_api.arguments 自由 JSON 绕过 pydantic 校验 的潜在风险在这 15 题里没有变成参数错误，但发现工具猜错名字 这一类是按需模式特有的新代价。

轮数因素要单独披露：最大 LLM 轮数 34， 12/14 题的 LLM 轮数不超过 v2 的 24 轮预算， 但 2 题（6c2c621_2, 6c2c621_3）用了 26 / 34 轮， 这两题的改善不能排除 48 轮预算的贡献。 停止原因分布：(无 stop 日志) × 1, cancelled × 14；状态分布：limit_reached × 2, success × 3, unfinished × 1, unsuccessful × 9。
一条必须披露的运行异常：57c3486_2 不是正常终止。 它在第 34 轮遭遇 FatalRunError: capability (ModelError: Model HTTP request rejected)， runtime 直接中止，因此是唯一一个没有 Runtime stopped 日志、也没有调用 finish 的 session；benchmark 仍按当时状态评分 （0.6，3/5 断言通过），落盘状态为 unfinished。 这是端点侧的一次性 infra 失败，不是按需 schema 引起的， 但它意味着这题的 0.6 是「被截断时的中间状态」，不能与其余 14 题的 完整终止等同看待。其余 14 题的日志里 ContextBudgetError 与超时均为 0。
边界：这仍不是新的官方成功率。 只重跑了 appworld-dev 57 题里原本未完成的 15 题， 没有重跑其余 42 题，也没有做全 57 题的正式 A/B； 单次运行、无跨环境重复，LLM 有随机性；只测了 on_demand + 48 一种组合， 还未拆分「省上下文」与「加预算」两个因素 （缺 on_demand + 24 组合）。 因此第 1 节主表的 appworld-dev 24/57 = 42.11% 一字未改；本附录的数字只能读作「这 15 题在按需 schema 下能做到什么」， 不能读作「v2 若换配置应该是多少」。
